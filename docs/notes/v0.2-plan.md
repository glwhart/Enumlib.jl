# v0.2 implementation plan

Live execution document for the v0.2 coding effort. Tracks chunks, milestones, status, and surfaced issues. The *design* lives in `research.md` (Phases 1–8); this file is the *execution* companion.

When v0.2 ships, this file is frozen as the v0.2 record. v0.3 gets its own `v0.3-plan.md`.

## Workflow

- **One chunk per session-or-two.** Each chunk has a clear "ends with" milestone and is a single PR-sized change.
- **Sequence:** I propose the design for the chunk, you sanity-check, I write the code with tests, you review the diff, we land it. Each chunk closes with a green test run.
- **Test-driven:** every chunk has tests against existing known counts (`test/runtests.jl` cases for FCC binary at n=4, 8, 12) or hand-verified examples. Tests live in `test/` from chunk 1 onward.
- **Commits:** small, frequent, with descriptive messages. Each chunk's "land" commit references this file (e.g., "Chunk 1: ParentLattice + SymmetryOp — closes v0.2-plan.md §Chunk 1").

## Working agreement (Gus + Claude)

Established during chunk 1 review. Goal: best-quality code with knowledge transfer, not dumbed-down code. Expanded slowly, the human-in-the-loop pace beats the rush-and-debug pace.

- **Best-code-with-teaching, not dumbed-down code.** Claude writes the most idiomatic Julia available. When a construct (`view`, parametric `where`, `hash` pairing, `do`-blocks, broadcasting) might be unfamiliar, Claude flags it inline or in the chunk's review document. Gus reads the explanation; if it lands, that idiom becomes part of the shared vocabulary; if not, Claude rewrites with more pedagogy. We don't trade code quality for legibility — we trade explanation effort.
- **No code is "approved" until both of us understand it.** Gus does a careful 4-eye review on every diff. If something is too clever to follow, Claude teaches it before the code lands. Slow, but correct, and over time the speed compounds as Gus's idiomatic-Julia vocabulary grows.
- **Reviews happen in dedicated docs.** Per chunk, Claude opens a `docs/notes/chunkN-review.md` with numbered items and "Your response:" slots. Gus responds inline; Claude responds to those responses; iterate until everything is locked. Then a single chunk commit lands.
- **Pause before committing.** Claude proposes a chunk's design before writing it; writes the code only after sign-off; then commits. (Chunk 1 went straight from work to commit because we were still calibrating the workflow; chunk 1.1 onward follows this rule.)
- **Comments explain *why*, not just *what*.** A comment like `# wrap into [0,1)` is redundant with the code. A comment like `# Periodic-coordinate gauge fix; matches ASE/pymatgen convention` says why. Claude defaults to the latter.
- **`Base.show` and other user-facing display functions: clear and complete over terse.** When the function is helping the user debug or understand the system, prefer a few extra lines of structured information over a one-line summary. Tools that help humans should optimize for the human, not for byte count. (Established during chunk 2 review.)
- **Don't reuse names from imported packages for our own functions** unless we're explicitly extending them (and qualifying the call). `using NormalForms` brings `snf` into scope; if Enumlib defines its own `snf(::Supercell)` accessor without explicit `import` or qualification, Julia treats it as a *new* function in the Enumlib namespace and shadows the imported one — same family of bug as chunk 2.1's `hash` shadow. Two precedents (chunks 2.1 + 3) suggest we should flag this for *every* new function definition: scan the imported-package APIs first; rename to something specific (`coloring_hash`, `lattice_rotations`) if there's any risk of collision. (Established during chunk 3 review.)

## Type-system glossary (chunk 1 spillover, reusable for chunks 2+)

Captured during chunk 1 review (see `docs/notes/chunk1-review.md` items 3–5). These terms recur throughout the v0.2 type catalog.

- **Thin wrapper.** A struct that exists to attach a *name* to existing data, with little or no transformation. `SymmetryOp{D}` wraps Spacey's `SpacegroupOp` (same fields: `R::Matrix{Int}`, `t::Vector{Float64}`). The "thin" part means we don't add fields, validate differently, or transform the data — we just rename so we can attach our own methods (without polluting Spacey's namespace) and add the parametric `{D}`.

- **Specialize.** Julia's compiler generates a *separate* compiled version of every function for each concrete type the function is called on. If we write `function apply(op::SymmetryOp{D}, x) where D` and call it with `D=3` and `D=2`, the compiler produces two distinct compiled functions, each with `D` baked in as a literal constant. The compiler can unroll loops of length `D`, omit array-bounds checks, etc. Static dispatch with runtime polymorphism. For 3D crystals (~99% of uses) the compiler treats `D` as a compile-time `3` — code as fast as if we hardcoded "3" everywhere. If we later want 2D, Julia generates a separate fast path automatically.

- **Parametric type / type variable / `where`.** `where D` introduces a type variable — like a generic parameter in Java/C++/TypeScript. Reading a signature `f(a::SymmetryOp{D}, b::SymmetryOp{D}) where D`: both arguments must be `SymmetryOp` parametric on the *same* `D`. The dispatcher binds `D` per call. Without `where D`, comparing `SymmetryOp{3}` to `SymmetryOp{2}` would type-check but probably crash inside; with `where D`, mismatched-D calls fall through to the default method (which usually returns `false` or throws `MethodError`). The single-`D` form expresses "same dimension" at the type level for free.

  *Common point of confusion*: in a one-liner like `Base.:(==)(a::SymmetryOp{D}, b::SymmetryOp{D}) where D = a.R == b.R && a.t == b.t`, `D` is the *type parameter* (an integer like 3) — NOT what the function returns. The function body `a.R == b.R && a.t == b.t` returns a boolean (the equality result), but `D` itself is always an integer dimension. They're two different things appearing in the same expression: D is bound at compile time to the dimension; the body is evaluated at runtime to produce true/false. You never see `D = true` or `D = false` — only `D = 3`, `D = 2`, etc.

- **Pairing rule (`==` and `hash`).** Any pair `(a, b)` where `a == b` MUST satisfy `hash(a) == hash(b)`. Otherwise hash-based collections (`Dict`, `Set`, `unique`) misbehave: equal values get sent to different buckets. Julia's default `hash` for a custom struct hashes the struct's *identity* (memory-like), not its contents — so two structurally-equal struct instances get *different* default hashes unless we override. Discipline: define `==` and `hash` together, both reading the same fields. The pattern `hash(op.R, hash(op.t, h))` chains hashes through the fields, mixing each into the seed `h` produced by the previous one.

- **`view` vs slice.** `view(A, :, j)` returns a *reference* into `A` (no copy); `A[:, j]` returns a *copy*. For read-only operations like computing a column norm, `view` is both faster (no allocation) and the idiomatic signal that we're not mutating. Use `view` whenever you don't need ownership of the data.

- **Hadamard ratio.** A scale-free measure of basis-matrix non-singularity: `|det(A)| / prod(‖aⱼ‖)` over the columns of `A`. Equals `1` for orthogonal columns, `0` for linearly dependent columns. Dimensionless — works regardless of unit choice. Used in `ParentLattice{D}` to detect numerically singular bases. Equivalent (inverse) of `MinkowskiReduction.orthogonalityDefect`.

**Bugs caught + fixed during chunk 7:**
- **Möbius inversion assumed normality.** First implementation built an "induced perm-group on H-orbits" and called `polya_count` on it. This is correct when `H` is normal in `G`, which is true for cyclic translation subgroups (SNF (1,1,n)) but not in general. At FCC n=4 HNFs 6 and 7 (SNF (1,2,2), giving non-cyclic T = Z/2 × Z/2), the K_2 subgroups are not normal in G; the induced action isn't well-defined. Fixed by switching to a non-normality-requiring formulation: `N_aper = (1/|G|) Σ_g Σ_H μ_T(H) · |fix(g) ∩ fix(H)|`, computing the joint-orbit partition of `{g} ∪ H_perms` via union-find for each (g, H) pair. Same Möbius coefficients on T's subgroup lattice; correct on every supercell shape we encounter.
- **Ag–Pt 1003 reference was a misremembered number.** I (Claude) asserted "1003 inequivalent structures (HNF 2012 Table 1)" in chunk 6 review without a verified source. The HF 2012 §4 application discusses "1536 (point group × translations) → ~400,000 distinct" — the 400,000 is for the *single canonical 2x2x2 conventional FCC HNF*, not summed across all 102 inequivalent HNFs at volume 32. Our `count_inequivalent(...; supercells = VolumeRange(32:32))` correctly returns ~1.2 billion when summed across all HNFs (HNFs with smaller stabilizers contribute disproportionately). The chunk-7 test plan had originally promised "Ag–Pt 1003" as the load-bearing literature reference; that test is dropped since the 1003 number was wrong. The actual chunk-7 validation is the 44-test cross-check against `length(enumerate(...))` at every chunk-5/6/6.2 locked reference value — strictly stronger than a single literature number would be. A future v0.2.0 polish task: pin down genuine HF-2012 reference counts (e.g., per-HNF counts at the canonical 2x2x2 supercell) and add them as additional regression tests.

**Scope (sub-chunks; design decisions locked from your 2026-05-08 inline review — see "Locked decisions" block below):**

- **11a. POSCAR writer.** `to_poscar(io, structure::EnumeratedStructure, parent, hnf, ...)` writes a single POSCAR in **VASP-5+ format** (compatible with VASP 5 and VASP 6 — the species-symbols line was introduced at v4→v5; v5→v6 didn't change the format). Line 1 is a comment we control; we pre-populate it with the identity metadata + an *energy slot* the calculator fills in:
  ```
  # enumlib_id=42 hnf=14 concentration=15:17 super_periodic=false energy_eV=
  ```
  The `energy_eV=` value is empty when written; collaborators fill it in by hand or short script after their DFT/MLIP job (per A1-(iv) lock). Format anchored against the VASP POSCAR specification only — **no Fortran-`makestr` cross-reference** (per Q6 lock).

Bulk write + manifest.** `write_enumeration(dir, enumeration; ...)` writes all structures into a directory plus an `enumeration.toml` manifest mapping `poscar_filename → (structure_id, hnf_idx, concentration, super_periodic_policy, ...)`. Directory bloat at scale (100k+ structures) acceptable for v0.2; alternatives (single binary archive) are v0.3+ polish.
- **11c. Roundtrip read.** `read_results(dir)` walks each POSCAR in the directory, parses the `energy_eV=` slot from line 1, returns a `Dict{structure_id → energy}`. `attach_results(enumeration, results)` then merges those energies onto the enumeration. **Energy-only schema for now** (per A2-(i) lock — CE code, energies are enough). Format is forward-compatible: a future `forces_eV_per_A=...` / `stress_eV_per_A3=...` slot can be added without breaking existing files.
- **11d. Tutorial + workflow doc.** A single end-to-end worked example (binary FCC training-database generation) that lives in `docs/notes/` initially, then becomes a Phase 13 tutorial. Demonstrates: enumerate → `write_enumeration` to a directory → ship to collaborator → receive POSCARs back with `energy_eV=` slots filled → `read_results` + `attach_results` → cluster-expansion fitting via JuCE.jl.

**Caveats:**

1. **Fortran is x86_64 via Rosetta on the M1.** A native arm64 build (blocked on this machine by missing Xcode CLT — `xcode-select --install` to fix) would likely make Fortran ~1.5× faster, widening the gap.
2. **Julia time excludes JIT warmup.** A throwaway `count_for_volume(2)` was called before the timing loop. Volume 1 still shows ~25 ms from second-pass specialization.
3. **Wall-clock vs CPU.** Fortran's per-volume "CPU" column was used for the table; total CPU summed to 5.6 s vs 5.8 s wall, so they're effectively the same. Julia is wall-clock from `@elapsed`.

**Read of the data.** Julia is within 1.2–1.7× of Fortran in the work-dominated middle (n=10–14), drifts to ~2× at n=16, and is dominated by per-call overhead at small n. The n=15 → n=16 jump (4.75 s → 12.2 s, 2.6× for a ~2.4× volume increase, vs Fortran's ~1.8×) is suggestive — work-per-structure is rising in Julia faster than in Fortran. First places to look when perf work starts: the `getPermG` + `getUniqueColorings` inner loop at high n (consistent with the StaticArrays profiling-pass note in v0.3+), and allocation patterns in the coloring deduplication.
