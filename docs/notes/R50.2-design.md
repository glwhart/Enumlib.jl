# R50.2 — Multilattice enumerate(...) — regime B (HF 2008/2009) (design)

Pre-implementation design doc for the second phase of cross-repo request R50 (JuCE → Enumlib). R50.1 (validation refactor, shipped as `54faefd`) replaced the misleading rejection message with a regime-discriminating cascade. R50.2 now ships the actual algorithmic enablement — letting `enumerate(...)` produce derivative structures for uniform multilattice parents (HCP, diamond, perovskite-uniform, slab, ...) via the HF 2009 extension of the HF 2008 algorithm.

**Background:** `docs/notes/R50.2-prep-notes.md` consolidates the math, algorithm, Fortran-engineering and current-Enumlib-state findings. This design doc references those notes by section number.

---

## 1. Goal

After R50.2 ships, the following call works end-to-end and produces the chunk-6-style locked-reference counts:

```julia
A_hcp = [1.0 -0.5 0.0; 0.0 sqrt(3)/2 0.0; 0.0 0.0 sqrt(8/3)]
parent = ParentLattice(A_hcp, [[0.0, 0.0, 0.0], [1/3, 2/3, 1/2]])
sites  = Sites(parent, [0, 1])                       # R51 convenience constructor
e = enumerate(parent, sites; supercells = VolumeRange(1:4))
length(e)                                            # → 201 (HF 2009 Fig. 6)
```

The R50.1 validation gate for regime B is *flipped* from "throw R50.2-pending" to "fall through to the HF 2009 path."

## 2. Locked decisions (from prep + user direction)

- **L1 (unified code path).** One `getPermG` handles any `n_D ≥ 1`. Single-lattice is the `n_D = 1` degenerate case. *Source: prep notes §3.1 comment.*
- **L2 (label-exchange policy).** Default is **not to eliminate** label-exchange duplicates. Materials scientists treat A↔B-swapped structures as distinct (different chemistry). Matches the current single-lattice behavior. *Source: prep notes §2.1 comment.*
- **L3 (site-ordering convention).** "Dset blocks": `flat_idx(d_i, g) = (i-1)·n + g_idx`. First `n` flat indices are dset position 1; next `n` are dset position 2; etc. *Source: prep notes §3, matches Fortran's `get_rotation_perms_lists`.*
- **L4 (stabilizer criterion).** Unchanged from single-lattice: rotation `N` is in the stabilizer iff `N` fixes the superlattice. The dset action is automatic once `N` is in. *Source: prep notes §4.*
- **L5 (super-periodicity).** Extends cleanly: translation subgroup `T` acts on `(d, g)` as `(d, g+τ)` — dset position preserved. Existing super-periodicity logic in `getUniqueColorings` should work unchanged on the bigger labeling vector. *Source: prep notes §5.*
- **L6 (dset-matching tolerance).** Default `eps_dset = 1e-6` (matches Fortran). Configurable via `ParentLattice(...; eps_dset = ...)` kwarg for power users. Sanity check at construction: if the precomputation finds no match for some op + dset position, throw with a diagnostic. Long-term (v0.3+ shopping list entry): refactor dset to `Rational{Int}` for fully exact arithmetic. *Source: user review of §3.2 — failure-mode analysis shows the safe eps range for natural inputs is wide (~1e-12 to ~1e-2); 1e-6 is comfortably in the middle.*

## 3. Implementation plan

### 3.1 Data structures

**`ParentLattice` extension** — cache the dset-permutation data computed once at construction.

```julia
struct ParentLattice{D}
    A::Matrix{Float64}
    dset::Vector{Vector{Float64}}
    space_group::Vector{SymmetryOp{D}}
    dset_perms::Vector{Vector{Int}}              # NEW: dset_perms[i] is π for space_group[i]
    dset_shifts::Vector{Vector{Vector{Int}}}     # NEW: dset_shifts[i][j] is v_j for space_group[i]
end
```

Computed inside the inner constructor immediately after `Spacey.spacegroup(...)` produces the multilattice space group. For single-lattice (`length(dset) == 1`), `dset_perms[i] = [1]` and `dset_shifts[i] = [[0,0,0]]` for every op (degenerate case, falls out for free).

### 3.2 New helper: `_dset_permutation(parent_basis, dset, op)`

Computes `(π, v)` for a single symmetry op by solving `N d_i + t = d_{π(i)} + v_i` for each `d_i`. Pure integer arithmetic in lattice coordinates (the math writeup's worked example shows the construction concretely). Used inside `ParentLattice`'s constructor.

**Tolerance:** the dset positions are floats (`1/3`, `2/3`, etc.). Per L6 lock: `eps_dset = 1e-6` default (matches Fortran), configurable via `ParentLattice` kwarg. The 1e-6 sits comfortably in the safe range `(1e-12, 1e-2)` for natural materials inputs:

- Float-precision error on one rotation `N × d_i` is ~1e-15 per coordinate (well below eps).
- Minimum pairwise dset distance in real materials is ~0.1–0.5 fractional (well above eps).

**Sanity check at `ParentLattice` construction.** If `_dset_permutation` finds no `d_j` within `eps_dset` of `N d_i + t (mod L)` for any op + dset position, throw with a diagnostic:
- *"No dset match for op #X at d_Y. Either `eps_dset` is too tight (try `eps_dset = 1e-4`) or this op isn't actually a multilattice symmetry (likely Spacey returned a spurious op — verify by inspecting `parent.space_group`)."*

**v0.3+ shopping list item** (added per this design): refactor dset to `Rational{Int}` arithmetic for fully exact lookup. Eliminates the whole tolerance question.

### 3.3 Extended `getPermG`

Current signature (single-lattice):
```julia
getPermG(h::AbstractMatrix, fixingOps::BitVector, LG::Vector{Matrix{Int}}) -> Vector{Vector{Int}}
```

Extend to:
```julia
getPermG(h::AbstractMatrix, fixingOps::BitVector, parent::ParentLattice) -> Vector{Vector{Int}}
```

(or a new method dispatching on `ParentLattice`). The new method:
1. Computes SNF transition matrix `T` from `h` (same as today).
2. For each fixing op:
   - Look up `(π, v)` from `parent.dset_perms[op_idx]`, `parent.dset_shifts[op_idx]`.
   - For each `(d_i, g)` pair, compute `(d_{π(i)}, g')` via the writeup's formula.
   - Pack into a length-`n_D·n` permutation using the dset-blocks convention (L3).
3. Compose with the supercell's translation group (each `τ ∈ G` gives a permutation `(d_i, g) → (d_i, g+τ)`).
4. Returns a `Vector{Vector{Int}}` of permutations on `n_D · n` sites.

When `n_D = 1`, this degenerates to the current single-lattice behavior. The `dset_perms[op_idx] = [1]` precomputation makes the dset-permutation step a no-op; the rest is identical to the existing algorithm.

### 3.4 `Supercell` extension

No struct change. `Supercell(hnf, parent)`'s constructor calls the extended `getPermG`. The `permutation_group` field now has length `n_D · n` permutations on `n_D · n` sites (vs `n` permutations on `n` sites today on multilattice parents — see prep notes §7.2 for the silent-wrong state today).

### 3.5 `_enumerate_exhaustive` (already works; just needs unblocking)

The existing body iterates `getUniqueColorings(k, sc.permutation_group)` which produces canonical-representative colorings. With the extended `sc.permutation_group`, the coloring vectors are length `n_D · n`. The existing super-periodicity loop in `getUniqueColorings` already works on the bigger vectors (it's structure-agnostic — just checks "labeling fixed by some non-identity translation," and translations are now `(d_i, g) → (d_i, g+τ)`).

**The only change to `_enumerate_exhaustive` is the validation gate flip in `_validate_enumerate_inputs`** — the regime-B branch transitions from "throw R50.2-pending" to "fall through."

### 3.6 EnumeratedStructure (small contract change)

`EnumeratedStructure.labeling::Vector{Int8}` was always length `n` for chunk-5/6. Post-R50.2 it's length `n · n_D`. Code that interprets the labeling needs to handle the dset structure:
- `to_labeling(s)`: still returns the raw `Vector{Int8}`. No change.
- `to_poscar(...)`: **now in scope** (per Q6 override). Emits POSCAR with `n · n_D` atoms. Site indexing follows L3 (dset blocks): the first `n` entries of the labeling are dset position 1; next `n` are dset position 2; etc. Species counts sum across dset positions when grouping atoms by species type in the POSCAR header. See §3.8 for details.

### 3.7 `count_inequivalent` / `estimate_cost` / `orbit_size`

- **`count_inequivalent`**: extends cleanly. The chunk-7 Möbius math works on any group action (prep notes §5.3). The translation subgroup `T` is unchanged; the per-(g, H) joint-orbit partition becomes a partition of `n_D · n` sites instead of `n`. Update the relevant cycle/orbit-counting helpers to consume the bigger perm group.
- **`estimate_cost`**: bitmap-size prediction is `k^(n_D · n)`. Update `_bitmap_bytes` and the memory model.
- **`orbit_size`** (R33): works unchanged. `_orbit_size(perm_group, coloring)` is algorithm-agnostic; it just needs matching-cardinality inputs, which the new perm group provides.

### 3.8 POSCAR I/O for multilattice (in scope per Q6)

`to_poscar(io, structure, parent, hnf)` writes a VASP-format POSCAR. Today it emits `n` atomic positions grouped by species. For a multilattice supercell with `n · n_D` total sites:

1. **Atomic positions** — emit `n · n_D` fractional positions. Per the L3 site-ordering convention: the first `n` positions are dset position 1 across the supercell (at the SNF-basis grid positions `g ∈ G` shifted by `d_1`); next `n` are dset position 2; etc. Compute via `supercell_fractional_positions(...)` extended to take the dset.
2. **Species counts** — for `k` species, the POSCAR species line lists per-species *total* counts summed across both dset positions. E.g., HCP binary with labeling `[0, 0, 1, 1]` (length 4 = 2·2): two A atoms total (one on each sublattice), two B atoms total. The `# enumlib_id=... concentration=A:B:..._total` header field is the *total* concentration across all dset positions.
3. **Header metadata** — same `# enumlib_id=...` line; the `concentration` slot reports `A:B:...` totals (R50.2 default — no per-sublattice breakdown). The `super_periodic` flag works as today (the existing super-periodicity check on the extended labeling vector).
4. **Roundtrip** — `write_enumeration_archive` and `read_results` / `attach_results` are unchanged; they're keyed by `structure_id`, agnostic to labeling length.

**Open question for §6:** for the species-counts line, do we want the option of per-sublattice species counts (sublattice A: 1 A + 1 B, sublattice B: 1 A + 1 B) in a future extended header, or always emit the summed total? My lean: total only for v0.2.0 — keeps the POSCAR format simple and matches VASP's flat per-species expectation. Per-sublattice tracking can be a v0.3 feature if user demand surfaces.
