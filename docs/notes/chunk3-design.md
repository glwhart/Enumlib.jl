## What lives in chunk 3

### `HNF{D}` — a validated supercell-defining matrix

```julia
"""
    HNF{D}

A Hermite Normal Form matrix in `D` dimensions: a lower-triangular integer matrix
with positive diagonal entries and sub-diagonal entries reduced into [0, diagonal).
Determinant `n = ∏ diag` is the supercell index (number of parent cells in the
supercell).
"""
struct HNF{D}
    matrix::Matrix{Int}    # D×D, lower-triangular, validated at construction
end
```

**Constructor (validates):**
- Inner: enforces lower-triangular structure (`m[i,j] == 0` for `j > i`), positive diagonal (`m[i,i] > 0`), sub-diagonal range (`0 <= m[i,j] < m[i,i]` for `j < i`).
- Outer infers `D` from `size(m, 1)`.

**Accessors:**
- `volume(h::HNF)` — product of diagonal entries.
- `Base.det(h::HNF)` — overload returning `Int`, equal to `volume(h)` (since lower-triangular det = product of diagonals).
- Equality + hashing via the standard pairing-rule pattern.

**Pretty printing:**
```
HNF{3} (volume 4)
  4  0  0
  1  1  0
  3  0  1
```

### `Supercell{D}` — HNF + cached symmetry data

```julia
"""
    Supercell{D}

A symmetry-inequivalent representative HNF, plus the cached SNF diagonal and
permutation group induced by parent symmetries that fix the superlattice.
Carries the per-supercell data the labeling enumeration in chunk 5 will reuse
across all colorings on this supercell.
"""
struct Supercell{D}
    hnf::HNF{D}
    snf::Vector{Int}                       # diagonal of SNF; length D, with s_1 | s_2 | ... | s_D
    space_group_order::Int                 # |stabilizer of this superlattice| within parent.space_group
    permutation_group::Vector{Vector{Int}} # permutations on n*nD supercell sites
end
```

**Construction:**
- `Supercell(hnf::HNF{D}, parent::ParentLattice{D})`: computes SNF, finds the stabilizer subgroup of `parent.space_group`, builds the permutation group from rotation + lattice translations.
- The permutation-group construction is the load-bearing port from the existing `getPermG` function in `src/Enumlib.jl`. Adapted to take `parent::ParentLattice{D}` (with its `space_group::Vector{SymmetryOp{D}}`) instead of the legacy `pLat`/`G`/`fixingOps` triple.

**Accessors:**
- `hnf(s::Supercell)`, `snf(s::Supercell)`, `space_group_order(s::Supercell)`, `permutation_group(s::Supercell)`.
- Equality + hashing for cache keys (an enumeration may need `Set{Supercell}` etc.).

**Pretty printing:**
```
Supercell{3} (n = 4, |stabilizer| = 12, |perm group| = 48)
  HNF: 4 0 0 / 1 1 0 / 3 0 1
  SNF diag: [1, 1, 4]
```

### `getSymInequivHNFs(n::Int, parent::ParentLattice{D}) → Vector{HNF{D}}`

Port of `getSymInequivHNFs` from `src/LatticeColoringEnumeration.jl`. Takes a parent and a supercell volume (index) `n`; returns the symmetry-inequivalent HNFs.

**Mapping from the legacy implementation:**
- Legacy signature: `getSymInequivHNFs(d, pLat, G::Vector{Matrix{Float64}})` — takes a raw matrix `pLat` and Cartesian-coord rotations `G`.
- New signature: `getSymInequivHNFs(n::Int, parent::ParentLattice{D})` — extracts what it needs from `parent`, including the lattice rotations from `parent.space_group`. The fractional translations (chunk 1's multilattice space-group machinery) don't affect HNF symmetry equivalence, so the rotation-only restriction is the one we use here. (HNF equivalence under Hart-Forcade 2008 step 2 is `H_2 ≅ H_1` iff there exists rotation `R` in the lattice point group such that `H_1 R H_2^{-1}` is unimodular. Pure rotations.)
- Internals: `getAllHNFs(n)`, `tripletList`, `basesAreEquiv` are reused as-is (they take integer matrices, no port needed). The wrapper translates between the new and legacy types.

**Returns:** `Vector{HNF{D}}` — one HNF per equivalence class, with the canonical representative chosen by the existing tie-breaking logic.

### `getFixingOps(hnf::HNF{D}, parent::ParentLattice{D}) → Vector{Int}`

Port of the existing `getFixingOps`. Returns indices into `parent.space_group` of the operations whose action on the lattice fixes the superlattice generated by `hnf`. These are the operations that contribute to `Supercell.permutation_group`.

(Same naming as the legacy function for continuity; the legacy version took a Cartesian-coord rotation list and is being subsumed by the new version.)

### Internals reused as-is

- `getAllHNFs(n)` — generates all `n_HNF` matrices at volume `n`. Pure integer, no parent.
- `tripletList(n)` — diagonal triplets summing to `n`. Pure integer.
- `basesAreEquiv(HNF1, HNF2, ...)` — equivalence test. Already exists in two flavors (Cartesian + lattice-coord); we use the lattice-coord one with `parent.space_group`'s rotations.

These don't change; we just call them from the new wrappers.

## Tests planned (`test/test_hnf.jl`)

Validates against existing test counts and adds new invariants for the new types.

### `HNF{D}` validation
1. **Inner-constructor validation.** Accept a valid lower-triangular HNF. Reject:
   - Non-square matrix.
   - Negative or zero diagonal.
   - Non-zero super-diagonal entry.
   - Sub-diagonal entry out of `[0, diagonal)` range.
2. **`volume` and `Base.det`.** Equal to product of diagonal; integer return type.
3. **Equality + hashing.** Two HNFs with the same matrix compare equal and hash equal; can be stored in a `Set`.

### `Supercell{D}` construction
4. **Simple cubic, n=2.** Build `Supercell(hnf, parent)` for a representative HNF; verify SNF diagonal, permutation group has 96 elements (48 rotations × 2 translations) for the cubic case.
5. **HCP, n=2.** Smaller stabilizer; verify the permutation group is the right size.

### `getSymInequivHNFs` against the existing test corpus
The existing test in `test/runtests.jl` has these reference counts for FCC primitive (the canonical test case):
- 4-site fcc: 7 inequivalent HNFs
- 8-site fcc: a known count (let me verify before locking)
- 12-site fcc: a known count

### Bridge between new and legacy
9. **Round-trip: `getSymInequivHNFs(n, parent)` returns `Vector{HNF{D}}`.** Convert each `HNF{D}.matrix` back to a `Matrix{Int}`, pass through the legacy `getSymInequivHNFs` and verify the results match (same set of representative HNFs, possibly in different order).

This last test is the safety net: if the new wrapper diverges from the legacy implementation, we catch it without rerunning the full FCC enumeration.

## Open question: terminology check

The legacy code uses both `LG` (lattice-coord rotations) and `G` (Cartesian-coord rotations) extensively. With the new `parent.space_group::Vector{SymmetryOp{D}}` carrying lattice-coord `R::Matrix{Int}` (per chunk 1 design), we're committing to the lattice-coord representation. The legacy `Cartesian` versions of `basesAreEquiv` and `getFixingOps` become unused. Worth deleting in chunk 3? Or keep around as "currently unused but matches the literature in some cases"?

My lean: **delete in chunk 3.** Less code surface; the lattice-coord versions are the ones the algorithm actually uses now. If a future chunk needs Cartesian versions (unlikely), git history has them.
> Me too. Let's drop. It's better to get the author (me) and any other developers (as well as the users of the code) thinking in integer represenation whenever possible. It's safer; no finite precision niggles.
